Приватность и сетевые обращения

Rosetun обращается в сеть следующим образом:

  • К VPN-серверу для туннеля; Пинг TCP также пробует установить TCP-соединение с каждым проверяемым сервером при отключённом туннеле.
  • Проверка URL и задержка на экране подключения отправляют сразу два HTTPS-запроса, к https://cp.cloudflare.com/generate_204 и https://www.gstatic.com/generate_204, через проверяемый сервер, текущий сервер или сервер каждого направления. Проверка URL соединяется с каждым сервером напрямую, мимо туннеля. При подключении и во время соединения служба отправляет те же запросы через текущий сервер, чтобы убедиться, что он работает; это не выключается.
  • К провайдеру подписки для загрузки и обновления серверов. По умолчанию отправляется User-Agent: Rosetun/<версия>. Ссылка подписки может содержать пароль; при HTTP-подписке токен передаётся без шифрования. Когда включено Отправлять ID устройства (по умолчанию), запрос содержит также:
    ЗаголовокWindowsLinux
    x-hwidХеш SHA-256, обрезанный до 16 байт, из MachineGuid и хоста сервера подпискиТо же из /etc/machine-id и хоста
    x-device-osWindowsLinux
    x-ver-osВерсия и сборка из реестраPRETTY_NAME из os-release
    x-device-modelМодель компьютера из BIOS или PCМодель из /sys/class/dmi/id/product_name или PC

    Сами MachineGuid и machine-id не отправляются, как и имя вашей учётной записи и адреса сетевых адаптеров. Разные серверы подписок получают разные ID, поэтому не могут сопоставить устройство; у подписок, добавленных до 0.4, ID прежний, один на все.

  • По адресам списков, которые указали вы или подписка: при добавлении и обновлении списка и вместе с обновлением подписок (выключается в Обновлять подписки автоматически). Rosetun отправляет ETag / Last-Modified прошлой загрузки, поэтому неизменившийся список заново не скачивается. Если туннель подключён, запрос идёт через него.
  • К настроенному DNS-over-HTTPS-резолверу через туннель. При подключении служба также проверяет DNS запросом example.com, а во время соединения задаёт вопросы о случайных именах под example.com.
  • К https://1.1.1.1/cdn-cgi/trace за внешним IP и страной на экране подключения: через текущий сервер при подключении (на Linux без правил по программам он идёт по вашим правилам, поэтому при «Напрямую» для этого адреса или по умолчанию покажет ваш собственный IP) и напрямую, когда туннель отключён, подключиться не удалось или служба недоступна. Внешний IP по умолчанию скрыт и не записывается в журнал. Направления отдельных запросов не делают: их страна берётся из имени узла.
  • К https://api.github.com/repos/eoftgge/rosetun/releases за списком релизов при запуске, если проверок ещё не было или с последней удачной проверки прошло больше суток, затем раз в сутки и по кнопке Проверить сейчас. Если GitHub отказывает из-за часового лимита (403 или 429), что бывает за общим адресом VPN, Rosetun читает вместо этого https://github.com/eoftgge/rosetun/releases.atom. Если туннель подключён, запрос идёт через него. Автоматическая проверка включена по умолчанию; выключить её можно в Настройки → О программе → Проверять обновления. Время последней удачной проверки, найденная версия, пропущенная версия и версия, о которой уже сообщил трей, хранятся в файле настроек. Ничего не скачивается и не устанавливается автоматически.
  • Проверка системы отправляет HTTP-запрос HEAD к http://cp.cloudflare.com/, без шифрования, чтобы сверить часы по заголовку Date. Она запускается по кнопке Проверить, сама после неудачного подключения и в Собрать отчёт; без туннеля запрос идёт напрямую, при подключении через туннель. Без подключения она также отправляет два DNS-запроса к 1.1.1.1, по UDP и по TCP, со служебным именем whoami.cloudflare и сравнивает ответы, чтобы понять, подменяет ли сеть DNS; Cloudflare видит ваш IP-адрес, как при любом DNS-запросе к нему. При подключении и пока kill switch держит защиту после сбоя DNS-запросов нет, а Собрать отчёт показывает последний результат, не спрашивая заново.
  • Если DNS перестаёт отвечать, сторож отправляет HTTP-запросы HEAD к 1.1.1.1:80 и к connectivitycheck.gstatic.com/generate_204 через туннель, чтобы отличить сбой DNS от потери связи. Второе имя определяется через DNS туннеля при подключении.
  • До подключения системный DNS разрешает имя VPN-сервера; операционная система также может разрешать имена провайдера и серверов при проверке пинга.
  • При смене сервера во время подключения имя нового сервера определяется через текущий туннель.

Что не отправляется: телеметрии и учётных записей Rosetun нет. Проверка обновлений приложения лишь сообщает о новой версии. Значки программ берутся с этого компьютера; на Windows у программы на сетевом диске или пути значка нет, так что показ значка никогда не обращается к другому компьютеру. С локальным API ядра и с Xray sing-box общается только через loopback.

В режиме прокси собственные запросы Rosetun, например обновление подписок, идут через локальный прокси, поэтому провайдер видит адрес VPN, как и в TUN.

При включённом Lockdown без подключения сам Rosetun (приложение и команда rosetun) по-прежнему обращается в сеть напрямую: к провайдеру подписки, к адресам списков, к cp.cloudflare.com для Проверки системы и с другими запросами выше, которые без подключения идут напрямую (проверки серверов, публичный IP, проверка обновлений). Другие программы нет. Провайдер подписки при этом видит ваш настоящий IP-адрес, как и без Lockdown.

Журналы остаются на этом компьютере.

  • Журнал службы на Windows лежит в data\logs в папке установки и доступен только администраторам, на Linux он в системном журнале и доступен root и читателям журнала (группы adm и systemd-journal в Debian). Собрать отчёт получает его только для учётной записи Windows, которая запускала подключение. На Linux он читает журнал от вашей учётной записи, без имени машины; если читать журнал нельзя, в отчёте будет пометка.
  • Когда Подробный журнал выключен, адреса назначения в сообщениях ядра заменяются на [hidden]. Имя или адрес VPN-сервера и причина ошибки могут остаться. Адреса сайтов попадают в журнал лишь при временно включённом Подробном журнале.
  • Локальная сеть записывает открытые сети в журнал службы, а публичную сеть только словом public.
